## Project overview

OpenKakutou `engine` is a Go library implementing the combat simulation for OpenKakutou fighting games: match/combat state, MUGEN CNS trigger/expression evaluation, state-machine execution, `.zss` script execution, physics/movement, hit detection, and damage/combo/round flow. It compiles to WebAssembly and depends on `character` (character data) and `stage` (boundary/camera data). It is org-wide — not tied to a single domain — and is consumed by `mode-*` game apps, starting with `mode-quick-versus`.

**Stack:** Go 1.26, compiled to WASM (`GOOS=js GOARCH=wasm`) for browser-based game modes. Currently stdlib-only; a Lua-compatible interpreter is anticipated as a future dependency for `.zss` script execution (backlog item 004), to be chosen during that item's own implementation, not before.
**Type:** library

## Scope of this repo <!-- keep -->

`engine` is combat simulation only — the simulation that runs while two characters fight:
- Match/combat state model (fighters, round/timer, position, facing)
- Trigger/expression evaluator for MUGEN CNS syntax
- State-machine execution (StateDef/Controller interpretation)
- `.zss` script execution (Ikemen GO's Lua-like state scripts)
- Physics and movement (velocity, gravity, ground/air, stage-boundary clamping)
- Hit detection (Clsn collision box resolution)
- Damage/health and combo resolution
- Input reading and command (`.cmd`) matching
- Round/match flow (win conditions, KO, timeout, reset) and the WASM entrypoint

Explicitly **not** in scope: menus, character selection, and overall game flow — that is `mode-*` territory (`mode-quick-versus` first). See `github.com/openkakutou/roadmap`'s `.vibe/decisions/004` and `.vibe/decisions/008`.

## Cross-repo dependencies <!-- keep -->

- `character` — character data (states, animations, sprites, `.cmd`/`.zss` parse output) that `engine` evaluates/executes at runtime. `character` stays a pure-data library; all evaluation and execution semantics live here.
- `stage` — boundary/camera data consumed by physics (stage-boundary clamping).

Both are read-only inputs to `engine` — this repo never writes back to either format.

## Development workflow (Vibe Coding)

The user is the **Product Owner only**. They describe requirements and evaluate outcomes — they do NOT write or manually test code.

### Definition of Done

A task is complete ONLY when ALL of the following are true:

- [ ] Implementation code is written
- [ ] Tests covering the nominal path exist and pass
- [ ] Tests covering edge cases and error paths exist and pass
- [ ] Lint exits with code 0 — `gofmt -l .` reports no files, `go vet ./...` is clean
- [ ] All tests pass — `go test ./...`
- [ ] No debug artifacts left in code (`fmt.Println` debug calls, commented-out code, etc.)

**Never present a result to the user if tests are failing.**

### TDD workflow

For every feature or fix:

1. **Write tests first** — describe expected behavior through tests before writing implementation
2. **Confirm tests fail** — run `go test ./...` and verify new tests fail (red)
3. **Write implementation** — minimum code to make tests pass
4. **Confirm tests pass** — run `go test ./...` and verify all tests pass (green)
5. **Refactor if needed** — clean up while keeping tests green
6. **Run lint** — run `gofmt -l .` and `go vet ./...`, fix any issues
7. **Present result** — summarize what was done, what was tested, and the test output

### Bug fix workflow

1. **Reproduce in a test first** — write a failing test that captures the bug
2. Fix the bug
3. Confirm the test passes
4. Present result with the test name that now covers the bug

### Self-correction loop

If tests or lint fail:
- Do NOT ask the user for help
- Diagnose the failure, fix it, re-run
- Repeat until green (max 3 self-correction attempts)
- Only escalate to the user if the failure reveals an ambiguous requirement

## Testing conventions

- Test location: co-located with source, `*_test.go` per package (e.g. `evaluator/eval_test.go` alongside `evaluator/eval.go`)
- Test runner: built-in `go test`
- One test file per source file
- Test names must describe behavior: `TestEvaluate_ReturnsError_OnUnknownTrigger`, not `TestEvaluate`
- Always cover: happy path + at least 2 edge cases + error/invalid input
- Fixture-driven integration tests (backlog item 009) use scripted real-character-vs-character scenarios, matching the org's existing practice (`character`) of validating against real files, not just hand-built data

## Constraints

- Never leave dead code or unused imports
- Never hardcode secrets — use environment variables
- Never skip tests to meet a deadline — fix the code instead
- Style is enforced by tooling, not by convention — always run `gofmt -l .` and `go vet ./...` before presenting results
- No rendering dependency: this module only simulates combat state — no OpenGL, no canvas, nothing rendering-related. It must compile cleanly to WASM
- Keep `character`/`stage` as read-only inputs — never add write/serialize logic for their formats here, that belongs in those repos
