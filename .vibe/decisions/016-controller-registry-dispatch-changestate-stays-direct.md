# 016. Controller registry dispatch keeps ChangeState direct, and takes Context by value

## Status
Accepted

## Context
Backlog item 012 asked for `statemachine.ApplyController`'s dispatch to become registry-based (a `map[string]func(...)`) instead of a hardcoded switch, so adding a controller type is an addition, not a modification of that function -- the SOLID review finding this item originated from. It was deliberately deferred twice (see the item's own Notes history) until backlog item 019 gave it a real second case (`PowerAdd`, alongside `ChangeState`/`VarSet`).

Two design attempts regressed this repo's own documented per-tick allocation discipline (`.vibe/decisions/009-011`, enforced by `TestTick_TickConfigAddsNoAllocationBeyondInputRecognition`'s `testing.AllocsPerRun` check):

1. **All three types in one registry, handler signature including the `exists func(int) bool` predicate and `*evaluator.Context`.** `Step`'s per-call closure `func(n int) bool { _, ok := states[n]; return ok }` went from "does not escape" to heap-escaping on every call (confirmed via `go build -gcflags="-m"`), because passing it into a call through a function value obtained from a map is an indirect call -- Go's escape analysis cannot prove the eventual callee won't store the pointer, so it conservatively forces it to the heap. Measured: 6 allocations per `Tick` call instead of the pinned 4.
2. **Registry handlers taking `*evaluator.Context`, `exists` kept out of the registry.** Removed the `exists`-closure regression, but `Step`'s own `&working` (the address of its local `Context`) now flowed into the same kind of indirect call for `VarSet`/`PowerAdd`, so `ctx` itself became a "leaking param" in `ApplyController` and forced `working` to escape instead. Still 6 allocations per `Tick` call.

## Decision
1. **`ChangeState` is not registry-dispatched.** It is the one controller type that both needs the `exists` predicate (to validate its target state) and controls `Step`'s loop termination (a `ChangeState` firing stops further controller processing for that tick) -- it is a control-flow primitive, not a generic state-controller side effect, and stays `ApplyController`'s one direct, statically-dispatched special case.
2. **Every other (non-state-changing) controller type dispatches through a registry** (`controllerHandlers map[string]ControllerHandler`, populated via `RegisterController`) whose handler shape takes `evaluator.Context` **by value** and **returns** the updated copy, never a pointer: `func(ctrl cns.Controller, ctx evaluator.Context) (evaluator.Context, error)`. `ApplyController` dereferences its own `*evaluator.Context` parameter once to call the handler, then writes the result back through the pointer. Passing a value (not an address) into the indirect call gives the compiler nothing to conservatively decide must live past the call, matching the by-value in/out shape this codebase already established for other freshly-built-and-returned per-tick values (`combat.ApplyHits`'s `match.MatchState`, `physics.Step`'s `FighterState`; see `.vibe/decisions/009-011`). Verified: `Tick` is back to 4 allocations per call, and `go build -gcflags="-m"` confirms `Step`'s own closure is un-escaped and `ApplyController`'s `ctx` parameter is only a "leaking param content" (its slice/map fields may be read elsewhere), not a full pointer escape.
3. `VarSet` and `PowerAdd` are registered as `RegisterController(ControllerTypeVarSet, applyVarSet)` / `RegisterController(ControllerTypePowerAdd, applyPowerAdd)` in the package's `init()`. Adding a future non-state-changing controller type (e.g. backlog item 020's `PlaySnd`) is one `RegisterController` call, never a change to `ApplyController` itself.
4. **The `evaluator.evalIdentifier`/`evalCall` half of item 012's acceptance criteria is deferred again**, left `status: todo`. `git diff 019027a..HEAD -- evaluator/eval.go` is still empty: no second real trigger/function-name need has appeared since the original deferral, unlike the `statemachine` half. Re-check when one does, per this repo's own "deliberately deferred until a real second case exists" convention already used for this same item.

## Consequences
- A future PR adding a new non-state-changing controller type touches only its own new handler function plus one `RegisterController` call -- `ApplyController`'s own code is unchanged, satisfying the original SOLID finding for this half of the item.
- Any future controller type that, like `ChangeState`, needs to see `exists` or control the loop cannot go through this registry without reopening this same allocation trade-off -- such a type should be evaluated on its own merits as a second direct special case, not forced into `ControllerHandler`'s shape.
- The registry's by-value shape means a handler cannot express "no change, leave ctx untouched" implicitly on error -- every error path returns a zero `evaluator.Context{}`, which is fine since `ApplyController` never writes it back on error (`*ctx` is only assigned on `err == nil`).
- This item's evaluator-side acceptance criterion remains open; item 012 itself is closed only for the `statemachine` half, tracked back into the backlog item's own Notes rather than silently dropped.
