# WebAssembly entrypoint

`cmd/wasm` builds the library into a WebAssembly module a browser (or any
JS host) can load directly — no local Go toolchain needed. It is thin glue
only: all real simulation logic lives in the root `engine` package and its
sub-packages (see [docs/architecture.md](architecture.md)), unit-tested
independently of this file.

## Building locally

```sh
GOOS=js GOARCH=wasm go build -o engine.wasm ./cmd/wasm
cp "$(go env GOROOT)/lib/wasm/wasm_exec.js" .
```

`cmd/wasm/main.go` is build-tag gated (`//go:build js && wasm`), so it is
invisible to a normal host build/test — `go build ./...` and `go test ./...`
never touch it.

## JS API

The module registers a single global, `globalThis.OpenKakutouEngine`, with
four functions: `newMatch`, `tick`, `resetRound`, `closeMatch`. Every
function takes and returns one JSON-encoded string in a uniform
`{ data, error }` envelope — exactly one field non-`null`, and the function
never throws (a Go panic is recovered at this boundary and reported as
`error` instead of tearing down the whole page's WASM instance). See
[docs/architecture.md](architecture.md#cmdwasm) for each function's exact
request/response shape and
[`.vibe/decisions/011-tick-orchestration-scope-and-wasm-session-design.md`](../.vibe/decisions/011-tick-orchestration-scope-and-wasm-session-design.md)
for why per-match runtime state stays Go-side in a session registry rather
than round-tripping through JSON on every call.

### Example

```js
const result = globalThis.OpenKakutouEngine.newMatch(JSON.stringify(request));
if (result.error) {
  throw new Error(result.error);
}
const { matchId, state, progress, animations } = JSON.parse(result.data);
```

## Verifying a build

`cmd/wasm/smoke.mjs` is a Node.js harness that loads a built module the same
way a browser would (via `wasm_exec.js`) and exercises `newMatch`, `tick`,
`resetRound`, and `closeMatch` — the closest thing to `go test` this file
has, since `syscall/js` code cannot run under the plain Go toolchain:

```sh
node cmd/wasm/smoke.mjs [path/to/engine.wasm]  # defaults to ./engine.wasm
```

## Release pipeline

`.github/workflows/release.yml` runs on every pushed tag matching
`v[0-9]*.[0-9]*.[0-9]*` (e.g. `v1.2.3`). It builds and tests the module
normally first (`go build ./...`, `go test ./...`, `go vet ./...`) —
nothing is published if any of those fail — then builds `engine.wasm` and
copies the matching `wasm_exec.js` (failing the build loudly if that file
isn't found at its expected path, rather than silently publishing a stale
or missing asset), publishing both as assets on that tag's GitHub Release
under stable, predictable names. `wasm_exec.js` is Go-version-specific
glue; the workflow always builds and copies it from the same Go toolchain
install that produced the `.wasm`, so the two published files are
guaranteed to be a matched pair — a consumer should always fetch both from
the same release, never mix versions.
