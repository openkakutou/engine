# Movement and state controllers: Ikemen GO units converted at the boundary, unsupported types reported by name

**Context:** Backlog 027 adds VelSet, VelAdd, VelMul, PosSet, PosAdd, ChangeAnim, CtrlSet, StateTypeSet, Turn, LifeAdd, LifeSet, Gravity and Null, each grounded in Ikemen GO (`src/bytecode.go` `Run` methods, `src/char.go` `lifeAdd`, `lifeSet`, `gravity`, `changeAnim`, `setAnimElem`, `setFacing`, `addX`, `setPosX`; required parameters from `src/compiler_functions.go`). Ikemen GO and the engine represent the fighter differently, and the engine had nowhere to read or report several inputs.

**Decision:**
- **Units.** Content values are Ikemen GO's: X facing-relative (positive forward), Y down. The engine stores world-space X and Y up (`match.Position`, `physics.Step`). Each handler converts: velocity/position X is multiplied by the facing sign (`VelSet`, `VelAdd`, `PosAdd`; `VelMul` is a plain factor), Y is negated. `PosSet` x is a world coordinate, not facing-relative, as in Ikemen GO. `Turn` flips `Facing` only: Ikemen GO also negates its facing-relative `vel[0]` so the world velocity is kept, which a world-space `Velocity.X` already does.
- **Divergences, accepted.** (1) Ikemen GO's `PosSet` x is `camera x + value` and y is `value + ground level`; the engine has no camera and its ground is 0, so the value is the stage coordinate. (2) Friction: Ikemen GO's physics S and C multiply `vel[0]` by the stand/crouch friction constants (char.go posUpdate); the engine has no friction constants, so S and C states get no friction. Not implemented, left to a follow-up item. (3) Ikemen GO's dynamic string form of `statetype`/`movetype` is not supported; an invalid letter is a descriptive error (Ikemen GO rejects it at compile time). (4) `LifeAdd` does not divide by the fighter's defense (the engine has none), so `absolute` is accepted but never matters; Ikemen GO's 32-bit overflow-to-KO rule is not reproduced.
- **Max health.** `statemachine.DefaultMaxHealth = 1000` (MUGEN's default life), hardcoded like `DefaultMaxPower` (decision 015): no per-character data feeds the engine.
- **Never revive.** Ikemen GO keeps a separate KO flag, so adding life to a KO'd fighter leaves it KO'd. The engine's `Alive` reads `Health > 0`, so `LifeAdd` and `LifeSet` leave a fighter at 0 health at 0.
- **No MoveTypeSet.** Ikemen GO has no such controller (its compiler's controller table has none); `StateTypeSet` sets the move type. It is not registered.
- **ChangeAnim element.** The engine tracks an animation position as `AnimTime` only. `ChangeAnim` sets `Anim`, restarts `AnimTime` at 0 and, when `elem`/`elemtime` are given, records `Context.AnimElem`/`AnimElemTime`; the root `Tick` resolves them to an `AnimTime` with the animation's frame durations (`resolveAnimElem`, Ikemen GO `setAnimElem` fallbacks) before the tick's regular `AnimTime++`, which is Ikemen GO's `anim.Action()` after the controllers. Unlike a `ChangeState` entry (`enterState`, no increment), a `ChangeAnim` therefore ends the tick at `AnimTime` 1.
- **Gravity and physics type.** Ikemen GO adds `yaccel` automatically only while the physics type is A (`char.go` posUpdate: `case ST_A: c.gravity()`); in any other physics type gravity comes from the Gravity controller. `Context.Physics` carries the current type: `enterState` takes the StateDef's (omitted means N as in `newStateBytecode`; U or an unknown letter keeps the previous, as `StateBytecode.init`) and `StateTypeSet physics` overrides it. `Tick` passes `physics.Step` the configured gravity only for A (`gravityFor`). The Gravity controller subtracts `Context.YAccel`, which `Tick` sets from `TickConfig.Gravity`. In an A state with a Gravity controller both apply, as in Ikemen GO. Before this, `physics.Step` applied gravity to any airborne fighter whatever the state's physics. Consequence: a state meant to fall must declare physics A (as KFM's common states do); `tick_test.go`'s physics test was the only existing test that relied on gravity in a state with no physics type and now declares A. Order, accepted: `physics.Step` adds gravity before integrating position, Ikemen GO after; unchanged here.
- **Physics runs after hit detection.** `VelSet`/`VelAdd` act on position only when `physics.Step` runs, after hit detection (pre-existing order); `PosSet`/`PosAdd` move the fighter before it.
- **Controller effects reach the result.** `Tick` previously copied only `StateNo` and `Power` from the post-statemachine `Context` onto `match.FighterState`. It now stores the whole `Context.FighterState` right after each fighter's tick, so position, velocity, facing and health changes reach hit detection, physics and `result.State` the same tick.
- **Unsupported reporting.** `ApplyController` no longer drops an unregistered type silently: it adds the lower-cased type to `Context.Unsupported` (once per type; `HitDef` excepted, `Tick` acts on it), reset by `Step` and surfaced as `Result.Unsupported`, the pattern of decision 017. The slice keeps its backing array between calls and `FighterRuntime.Unsupported` accumulates a tick's names in a second reused buffer, so reporting allocates nothing once warm; `TickResult.Unsupported` aliases that buffer and is valid until the next `Tick`. Controller types are lower-cased once per spelling (`lowerTypes`), and `ChangeState` is matched with `strings.EqualFold`, so dispatch allocates nothing per fired controller. `Tick` merges the special states and the current state into `TickResult.Unsupported [2][]string`; `cmd/wasm` adds a JSON `unsupported` array per side (`[]`, never `null`). `zssexec.Result.Unsupported` mirrors it. The tick does not fail.
- **-0.** X conversions go through `worldX`/`noNegativeZero`, so a zero never becomes `-0`, which would serialize as `-0` in the WASM JSON.
- **.zss parameter keys** are lower-cased by `zssexec`, as `cns` does, since Ikemen GO's are case-insensitive.

**Rejected alternatives:**
- *A `MoveTypeSet` controller* -- not in Ikemen GO; inventing it would accept content no reference engine accepts.
- *Failing the tick on an unsupported type* -- real characters use many unimplemented types every tick; a failure would stop every run. Reporting keeps the character playable and the gap visible.
- *Handling `elem` inside the handler* -- it has no animation data and the registry's handler shape (decision 016) cannot take it.
- *Passing max health and `yaccel` through `ApplyController`'s signature* -- it is shared with `zssexec` (decision 008); `Context` fields (`YAccel`) and a constant follow the existing channel.

**Allocation:** `ApplyController` used to lower-case the controller type and the `ChangeState` constant on every call: 2 allocations per fired controller (PowerAdd measured 350 ns, 24 B, 2 allocs). Now PowerAdd, VelSet, Turn, LifeAdd, ChangeAnim and an unsupported type all measure 0 allocs, 0 B per `ApplyController` call. `Result.Applied` (one slice per `Step` with a firing controller) is the one pre-existing allocation left; the root allocation tests compare supported and unsupported ticks against an equal number of PowerAdd controllers firing.
